    1. סיכום מנהלים (Executive Summary)

    1.1 מטרת הפרויקט

    לבנות מערכת ניהול אירועים מרכזית עבור "מיפל — גן אירועים בעיר", שתחליף תהליכים ידניים (Excel, WhatsApp, ניירת) בזרימת עבודה דיגיטלית אחודה: מרגע שמירת אופציה בלוח השנה, דרך סגירת הזמנה וחתימה דיגיטלית, ועד הפקת האירוע, קבלת לקוח בזמן אמת, גביית תשלומים ומשוב לאחר האירוע.

    1.2 הבעיה שהמערכת פותרת

    אולמות אירועים בישראל מתמודדים עם:

    • כפילויות וחפיפות — הזמנת אותו תאריך/משבצת פעמיים
    • פיזור מידע — פרטי לקוח, תפריט, תשלומים וחוזה במקומות שונים
    • עומס תפעולי — מעקב אחר אופציות שפגו, צ'קי ביטחון, טפסי הפקה ותזכורות ידניות
    • חוסר שקיפות — קשה לדעת מה קורה "עכשיו" באירוע LIVE
    • משוב לא מסודר — אין מנגנון מובנה לשליחת סקרים וניתוח שביעות רצון

    1.3 ערך עסקי צפוי

    יעדמדד הצלחה (KPI)
    מניעת כפילויות0 אירועים כפולים באותה משבצת (אילוץ DB ייחודי)
    קיצור זמן סגירת הזמנהמ-< 2 שעות ידני ל-< 30 דקות דיגיטלי
    שיפור גבייהירידה בצ'קי ביטחון חסרים (התראות אוטומטיות)
    שביעות רצון לקוחות> 60% מילוי משוב תוך 7 ימים
    יעילות צוותגישה מיידית לכל מידע האירוע מלוח בקרה אחד

    1.4 היקף (Scope)

    בהיקף (In Scope):

    • לוח שנה דו-תאריכי (עברי + לועזי)
    • ניהול אופציות והזמנות
    • טפסי הפקה + תוכנית ישיבה
    • קבלה LIVE באירוע
    • הגדרות מתחם (תמחור, שירותים, כשרות, משתמשים)
    • משוב לקוחות + סטטיסטיקות
    • שליחת ברכות (מיידית / מתוזמנת)
    • אינטגרציות: Google Auth, EasyCount (3 סוגי מסמכים), אימייל, WhatsApp API רשמי, S3
    • RBAC — 4 תפקידים מוגדרים (Manager, Staff, Production, Floor Staff)
    • מיגרציית נתונים היסטוריים מ-Excel (2026–2027)

    מחוץ להיקף (Out of Scope — שלב ראשון):

    • אפליקציית מובייל Native
    • פורטל לקוח מלא (צפייה בחוזה / תשלום עצמאי)
    • סליקת אשראי מקוונת (Cardcom / Tranzila) — תשלומים ידניים בלבד
    • CRM חיצוני / ERP
    • ניהול מלאי מטבח בזמן אמת

    2. פרסונות משתמשים והרשאות (User Personas & Permissions)

    2.1 פרסונות

    פרסונה 1: מנהל/ת האולם (Manager)

    • תיאור: בעל/ת העסק או מנהל/ת תפעולי/ת עם גישה מלאה
    • מטרות: פיקוח על לוח שנה, אישור הזמנות, מעקב כספי, ניהול הגדרות
    • כאבים: חוסר תמונה מלאה, תזכורות ידניות ללקוחות
    • תדירות שימוש: יומיומית

    פרסונה 2: מזכירות / נציג מכירות (Staff)

    • תיאור: עובד/ת שסוגר אופציות והזמנות, מתקשר עם לקוחות
    • מטרות: שמירת אופציה מהירה, שליחת הודעות, סגירת הזמנה
    • כאבים: טעויות בהזנת נתונים, חיפוש הזמנות ישן
    • תדירות שימוש: יומיומית

    פרסונה 3: מפיק/ת אירועים (Production)

    • תיאור: אחראי/ת על טופס הפקה, תפריט, סידורי ישיבה, כשרות
    • מטרות: השלמת טופס הפקה לפני האירוע, ייצוא תוכנית ישיבה
    • כאבים: שינויים אחרונים שלא מתועדים
    • תדירות שימוש: לפי אירוע

    פרסונה 4: צוות קבלה / אולם (Floor Staff)

    • תיאור: מבצע קבלת לקוח בזמן האירוע (LIVE)
    • מטרות: עדכון מנות בפועל, תוספות LIVE, חתימת לקוח
    • כאבים: טפסים ניירתיים, חוסר סנכרון עם ההזמנה
    • תדירות שימוש: ביום האירוע

    פרסונה 5: לקוח קצה (Customer — Guest)

    • תיאור: זוג/משפחה שהשלימו אירוע
    • מטרות: מילוי משוב קצר (אוכל / שירות / אולם)
    • גישה: דף ציבורי בלבד (/feedback/:token), ללא התחברות
    • תדירות שימוש: חד-פעמית

    2.2 מודל הרשאות (RBAC)

    המערכת מיישמת בקרת גישה מבוססת תפקידים (Role-Based Access Control) עם 4 תפקידים פנימיים ותפקיד חיצוני אחד. כל משתמש פנימי מאומת באמצעות Google OAuth ומשויך לרשומה בטבלת AuthorizedUser עם שדה role ייעודי.

    תפקידתיאוראימותהרשאות עיקריות
    Manager (מנהל/ת)בעל/ת העסק או מנהל/ת תפעולי/תGoogle OAuth + AuthorizedUserגישה מלאה לכל המערכת: הגדרות, מחיקות, נתונים כספיים, ניהול משתמשים, הפעלת LIVE
    Staff (מזכירות / מכירות)עובד/ת קבלה ומכירותGoogle OAuth + AuthorizedUserצפייה בלוח שנה, יצירת אופציות, המרה להזמנות, שליחת הודעות. ללא הגדרות מערכת וללא מחיקות
    Production (הפקה)מפיק/ת אירועיםGoogle OAuth + AuthorizedUserעריכת טפסי הפקה, תוכנית ישיבה, ניהול תפריט, גלריה. ללא גישה להזמנות, הגדרות או נתונים כספיים
    Floor Staff (צוות קבלה)עובד/ת אולם ביום האירועGoogle OAuth + AuthorizedUserגישה אך ורק למסך קבלה LIVE ביום האירוע
    Customer (לקוח קצה)ממלא משוב לאחר אירועToken חד-פעמי (/feedback/:token)שליחת משוב בלבד
    לא מורשה——נחסם בכניסה

    יישום טכני:

    • שדה role ב-JWT ובטבלת AuthorizedUser (ערכים: manager, staff, production, floor_staff)
    • Middleware requireRole(...) בצד השרת לכל endpoint רגיש
    • סינון פריטי תפריט ניווט (navConfig) ונתיבי Router בצד הלקוח לפי תפקיד
    • רק Manager רשאי לנהל משתמשים מורשים ולהקצות תפקידים

    3. דרישות פונקציונליות (Functional Requirements)

    3.1 מפת מסכים וניווט

    התחברות (Google)
    └── לוח בקרה (Dashboard)
            ├── לוח שנה (Calendar) ──► פופאפ יום ──► אופציה / הזמנה / LIVE
            ├── הגדרות מתחם (Settings)
            ├── ניהול אופציות (Options Manager)
            ├── ניהול הזמנות (Bookings Manager)
            ├── משובי לקוחות (Feedback Manager)

    תפריט צד (RTL): מגירה נפתחת מימין, כותרת אחידה בכל מסכי האדמין.

    3.2 מודול 1: התחברות ואבטחה

    FR-AUTH-01: התחברות Google

    • כפתור "התחברות עם Google" במסך מרכזי
    • בדיקה מול טבלת AuthorizedUser — רק אימיילים מורשים
    • JWT ב-cookie (Access 1 שעה, Refresh 7 ימים) + CSRF protection

    FR-AUTH-02: ניהול משתמשים מורשים ותפקידים

    • הוספה/מחיקה של אימיילי Google בהגדרות מתחם
    • הקצאת תפקיד RBAC (manager / staff / production / floor_staff) לכל משתמש
    • רק Manager רשאי לנהל משתמשים ולשנות תפקידים

    FR-AUTH-03: התנתקות

    • ניקוי session + redirect למסך התחברות

    3.3 מודול 2: לוח בקרה (Dashboard)

    FR-DASH-01: תצוגת KPI

    • ממוצע משוב חודשי (אוכל / שירות / אולם)

    FR-DASH-02: אירועים קרובים

    FR-DASH-03: מיני-לוח שנה

    • תצוגה חודשית מקוצרת עם ניווט מהיר ללוח המלא

    FR-CAL-01: תצוגת חודש RTL

    • עמודות: שבת → ראשון
    • תאריך עברי + לועזי בכל תא
    • ניווט חודשים, סינון לפי סוג אירוע

    FR-CAL-02: קידוד צבעים למשבצות זמן

    FR-CAL-03: סטטוסים בלוח

    3.5 מודול 4: שמירת אופציה (Option)

    FR-OPT-01: טופס אופציה קצר

    • תאריך (ממולא מראש), סוג אירוע, שמות לקוח א/ב, טלפון, הערות
    • בחירת משבצת זמן
    • משך תפוגה (ברירת מחדל: 48 שעות — מ-SystemSettings)

    FR-OPT-02: ניהול אופציות (Options Manager)

    • טבלה: תאריך, שמות, סוג, משבצת, תפוגה, פעולות
    • חיפוש וסינון
    • פעולות (לפי RBAC): הודעה ללקוח (WhatsApp/Email), סגירה להזמנה; מחיקה — Manager בלבד

    FR-OPT-03: הודעת אופציה

    • מודל עם תבנית הודעה מותאמת
    • שליחה בערוץ נבחר: WhatsApp API רשמי (Green API / Twilio) או Email
    • מעקב סטטוס משלוח (נשלח / נכשל) ורישום בלוג

    FR-OPT-04: מדיניות תפוגה

    • אופציה שפגה נשארת על הלוח עד סגירת אירוע אמיתי או שחרור ידני (POST /api/bookings/release)

    3.6 מודול 5: הזמנה (Booking Form)

    FR-BOOK-01: MetaBar

    • קוד אירוע ייחודי (eventCode), סטטוס, תאריך

    FR-BOOK-02: פרטי לקוח א' ו-ב'

    • שם מלא, ת.ז., טלפון, אימייל, כתובת

    FR-BOOK-03: הגדרות אירוע

    • סוג: חתונה / אירוסין / בר מצווה / אחר

    • משבצת זמן, מספר אורחים, מינימום אורחים, כשרות, מוזיקה, קוד עוקב

    FR-BOOK-04: תשלומים (רישום ידני)

    הבהרה: בשלב זה אין אינטגרציה לסליקת אשראי מקוונת. כל התשלומים מנוהלים ונרשמים ידנית במערכת.

    • מחיר בסיס לאורח, מע"מ (17–18%), תוספות אולם, תוספות חיצוניות
    • אמצעי תשלום נתמכים: מזומן / העברה בנקאית / צ'ק בלבד
    • סריקת צ'ק (OCR): מצלמה + Tesseract לזיהוי מספר צ'ק, בנק, סניף, תאריך
    • תבניות תנאי תשלום (paymentTemplates)
    • רישום סכומים ששולמו (paidAmount, advancePaid, totalPaid) ללא חיוב אוטומטי

    3.8 מודול 7: טופס הפקת אירוע (Event Production Form)

    3.15 זרימות משתמש מרכזיות (User Flows)

    זרימה 1: אופציה → הזמנה

→ מילוי טופס קצר → שמירה (סטטוס OPTION)
→ [תפוגה / המשך] → "סגור להזמנה" → טופס הזמנה מלא
→ תשלום + חתימה → שמירה (סטטוס BOOKED)

    זרימה 2: הזמנה → הפקה → LIVE

    ניהול הזמנות → בחירת הזמנה → טופס הפקה
→ תפריט + תוכנית ישיבה → שמירה
→ [יום האירוע] → באנר אוטומטי "אירוע היום"
→ Manager לוחץ "פתח אירוע LIVE"
→ Floor Staff / Manager: טופס קבלה (עם Fallback Offline)
→ תוספות LIVE + חתימה → סגירה → חשבונית חיוב (EasyCount)

    זרימה 3: אירוע → משוב

    [Cron: סיום אירוע] → יצירת Feedback + Token
→ שליחת קישור ללקוח → מילוי דף ציבורי
→ עדכון סטטיסטיקות + התראה למנהל

    7.4 מיגרציית נתונים היסטוריים (Data Migration)

    DR-MIG-01: ייבוא אירועים מ-Excel

    מטרה: ייבוא הזמנות קיימות לשנים 2026–2027 מקובץ Excel מרכזי, כדי למנוע double-booking של תאריכים שכבר תפוסים במערכת הישנה.

    פקודת הרצה:

    npm run db:import-legacy -- --file=./data/legacy-bookings-2026-2027.xlsx

    דרישות הסקריפט:

    דרישהתיאור
    קלטקובץ Excel מאסטר (legacy-bookings-2026-2027.xlsx) עם עמודות: תאריך, משבצת, סוג אירוע, שמות לקוח, טלפון, מספר אורחים, קוד אירוע (אופציונלי)
    ולידציהבדיקת כפילויות לפני ייבוא; דילוג על שורות שגויות עם דוח שגיאות
    מיפוייצירת EventDate + Booking (סטטוס BOOKED, isOption: false)
    אילוץשמירה על @@unique([calendarDateId, timeSlot]) — עצירה והתראה במקרה של התנגשות
    דוחסיכום: יובאו / דולגו / נכשלו; קובץ לוג import-legacy-report.json
    הרצהחד-פעמית לפני go-live; ניתן להרצה חוזרת במצב idempotent (דילוג על קיימים)

    תלות: יש להשלים את המיגרציה לפני הפעלת המערכת בפרודקשן, כדי שהלוח שנה ישקף את כל האירועים התפוסים.
