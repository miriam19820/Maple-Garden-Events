    גרסת מסמך: 1.0

    מבוסס על: קוד המקור בפרויקט Maple-Garden-Events

    תקציר מנהלים

    מיפל היא מערכת Full-Stack לניהול אולם אירועים: לוח שנה דו-תאריכי, אופציות והזמנות, הפקה, קבלה LIVE, תשלומים, חוזים, משוב לקוחות ותקשורת אוטומטית. הארכיטקטורה בנויה כ-Monorepo עם שני רכיבים עיקריים — אפליקציית אדמין ב-React ושרת API ב-Node.js — המתקשרים ב-REST וב-WebSockets מול בסיס נתונים PostgreSQL.

    המערכת מיועדת לצוות פנימי קטן (מנהלים, מזכירות, הפקה, קבלה) ולדף משוב ציבורי חד-פעמי ללקוחות. היעד התפעולי הוא אמינות, מניעת כפילויות, וסנכרון בזמן אמת — לא עומס של אלפי משתמשים ציבוריים.

    2.4 אינטגרציות חיצוניות

    Google OAuth

    1. המשתמש מתחבר ב-Google בצד הלקוח
    2. ID Token נשלח ל-POST /api/auth/login
    3. השרת מאמת מול Google, בודק AuthorizedUser, מנפיק cookies

    EasyCount (חשבוניות)

    • מצבי הפעלה: off | simulation | sandbox | live
    • ברירת מחדל: simulation (ללא credentials)
    • סטטוס נשמר ב-Booking.easycountStatus
    • Fallback: המשך תפעול גם בכשל API

    WhatsApp (Green API)

    • שליחת תזכורות (צ'ק ביטחון, טופס הפקה, תפריט)
    • בדיקת existsWhatsapp לפני שליחה
    • Fallback לאימייל במקרה כשל

    אימייל (Nodemailer)

    • תזכורות תפעוליות וכספיות
    • משוב אוטומטי לאחר אירוע
    • התראות מנהל (כשרות, חובות)

    Puppeteer (PDF)

    הפקת חוזים חתומים וטפסי הפקה להורדה.

    Tesseract (OCR)

    זיהוי פרטי צ'ק ביטחון מצילום (צד לקוח).

    AWS S3

    • מיושם: גיבוי DB דחוס (pg_dump → .tar.gz → S3)
    • בתכנון: העלאת חתימות, צ'קים, גלריה — Presigned URLs + SSE

    2.6 זרימת נתונים לדוגמה — שמירת הזמנה

    1. משתמש בוחר תאריך בלוח שנה (Client)
2. POST /api/bookings עם פרטי לקוח ומשבצת
3. Server:
   a. ולידציה (Zod)
   b. בדיקת זמינות משבצת (bookingDateValidation)
   c. יצירת Booking + EventDate (Transaction)
   d. אילוץ DB @@unique מונע race condition
4. emitBookingUpdated() → Socket.io
5. כל הלקוחות: invalidateQueries → לוח שנה מתעדכן

    3. מטרות על ויכולות ביצועים (Scale & Performance)

    3.1 יעד סופי של המערכת

    ממדיעד
    משתמשים פנימיים5–15 משתמשים במקביל (צוות אולם)
    לקוחות קצהדף משוב ציבורי — עומס נמוך, חד-פעמי
    אירועים פעיליםמאות הזמנות בשנה (2026–2027+)

    הערת הקשר: דרישה של 1,000 משתמשים בו-זמנית רלוונטית בעיקר לפלטפורמות ציבוריות. מיפל היא מערכת B2B פנימית — פרופיל העומס האמיתי הוא עשרות בקשות בדקה בשיא (יום אירוע LIVE), לא אלפי חיבורים. הארכיטקטורה הנוכחית מתאימה לפרופיל זה.

    4. סיכום והמלצות לצוות

    נקודות חוזק

    1. הפרדה ברורה בין Client / Server / DB עם API מובנה
    2. מניעת double-booking בשלוש שכבות: ולידציה, אילוץ DB, טיפול ב-conflict
    3. סנכרון בזמן אמת לצוות מרובה משתמשים
    4. אבטחה מרובת שכבות: OAuth, JWT, CSRF, Rate Limit, Helmet
    5. תפעול אוטומטי: Cron jobs, גיבויים, התראות
    6. ניטור: Winston + Sentry + request duration logging

    פערים להשלמה לפני Go-Live

    1. RBAC מלא — הוספת role ל-AuthorizedUser + middleware requireRole
    2. Fallback Offline במסך LIVE — localStorage + sync
    3. S3 לקבצים — חתימות, צ'קים, גלריה (Presigned URLs)
    4. השלמת בדיקות E2E — Playwright Golden Path עם auth mock
    5. Load test — אימות עומס יום אירוע (10–20 משתמשים מקבילים)
